# 001 - Monsters catalogue in its own Postgres database

Issue: #35 (US-10, US-11). Status: accepted.

## Decision

- **One Postgres per service** (Lab 05, data ownership). `monsters-db` is used only
  by the monsters service. It sits on a private Compose network (`monsters-data`,
  `internal: true`) that only the monsters service joins, so no other container
  can reach it.
- **Seed loaded at every start, as an upsert.** The service validates
  `seed/monsters.json` and `seed/images/` and writes them in one transaction with
  `INSERT ... ON CONFLICT DO UPDATE`. Restarting twice gives the same table, and
  editing the seed only needs a restart. If the seed is broken, the service
  refuses to start.
- **Images stored in the database (BYTEA)**, served by `GET /monsters/{id}/image`.
  The whole catalogue (data + images) is in one store with one owner, as the
  issue asks. The JSON only returns `image_url`; the client fetches the image with
  a second request (allowed by the requirements, section 4).
- **The seed is validated with an allow-list** (Lab 08): known elements and
  rarities, stats 1-255, unique ids, images must be real PNGs inside
  `seed/images/` (no path traversal).
- **Driver: pg8000**, a pure-Python Postgres driver. No system library to install
  in the image (smaller attack surface, nothing extra for Trivy to flag), and it
  takes a standard `ssl.SSLContext`, so certificate checking is the same code as
  everywhere else in the project.
- **TLS to the database** (Lab 08). Postgres runs with `ssl=on` and `pg_hba.conf`
  only accepts `hostssl` + `scram-sha-256` over the network. The service verifies
  the DB certificate against our CA and the name `monsters-db`.
- **Password as a Docker secret** (`/run/secrets/db_password`), generated by
  `certs/generate-certs.sh`, never in the repository.
- **Containers as non-root**: the DB runs as the image's `postgres` user.

## Consequences

- The catalogue is read-only for players. Nothing writes to it at runtime except
  the seed step, so there is no risk of players changing monster stats.
- One database connection per request. Simple and safe for now; if the Locust
  tests show it is a bottleneck, add a small connection pool.
- The images are about 1 MB each. Fine for a lab project, but resizing them
  (e.g. 256x256) would make the catalogue screen and the performance tests faster.
